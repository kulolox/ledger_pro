## 4. 关键缺陷发现与修复记录 (Defect & Fix Log)

在本次真机全量回归中，针对原生 Hybrid 环境下的特殊机制，共发现并彻底修复了 4 项关键缺陷：

### 4.1 缺陷 1：Android WebView / Weex 环境下原生 WebCrypto 缺失
- **现象描述**：点击登录按钮时弹窗报错 `当前环境不支持 webcrypto`，登录请求未发出。
- **根本原因**：部分较低版本 Android 系统的 WebView 或 5+App 运行时在非绝对 HTTPS / 本地 `file://` 协议下未挂载原生 `window.crypto.subtle` API。
- **修复方案**：引入高性能、纯 JS 实现的标准 RSA-OAEP 加密方案，在 `front_end/src/utils/crypto.ts` 中实现跨端安全的纯算法库，支持 SHA-256 填充与 PEM 公钥解析，彻底摆脱系统底层 WebCrypto 限制。
- **验证结果**：真机一键成功完成公钥加密、后端解密校验通过、无感下发 Token。

### 4.2 缺陷 2：Weex/JSCore 下 `toLocaleString` 国际化精度丢失
- **现象描述**：真机主页流水与概览卡片金额渲染异常，出现 `+1890.0886329999998万` 浮点数长尾及截断省略号。
- **根本原因**：Android 5+App 运行时的 JavaScriptCore 引擎缺失完整的 `Intl` 国际化实现，对 `toLocaleString(locale, {minimumFractionDigits: 2})` 传入的 options 直接忽略，导致四舍五入失效和 JavaScript 浮点数二进制精度泄漏。
- **修复方案**：重构 `front_end/src/utils/format.ts` 中的 `formatNumber` 与 `formatAmount` 方法，统一采用底层数学运算 `toFixed(2)`，并结合高鲁棒性正则表达式添加千分位分节符，杜绝运行环境依赖。
- **验证结果**：所有金额在真机上均严格保留 2 位小数（如 `¥1,890.00`），无任何浮点溢出。

### 4.3 缺陷 3：空账本概览卡片展示 `-0` 负零字符
- **现象描述**：切换到新创建或无支出流水的账本时，主页和统计页面的总支出卡片显示 `-0`。
- **根本原因**：代码中直接将 `formatAmount(-item.amount)` 或拼接 `'-'`，当 `amount == 0` 时产生 `-0` 视觉缺陷。
- **修复方案**：在 `front_end/src/pages/index/index.vue` 及 `front_end/src/pages/statistics/index.vue` 中增加符号判定：仅当金额严格大于 0 时渲染前置负号，为 0 时标准显示 `0.00`。
- **验证结果**：零账单状态下清晰展示 `¥0.00`，UI 规范统一。

### 4.4 缺陷 4：App 端逻辑层无 DOM 导致统计页面图表白屏
- **现象描述**：进入“统计”页面时，原本用于 Web 端的 `EChart.vue` 组件内部由于无法通过 `document.getElementById` 获取 DOM，图表容器高度虽然占位但内部完全白屏空白。
- **根本原因**：uni-app 在 App 模式下采用双线程架构，逻辑层（JS VM）无法直接触达视图层 DOM，原版 ECharts 依赖浏览器 Canvas/SVG 导致无法渲染。
- **修复方案**：在 `front_end/src/pages/statistics/index.vue` 中，用现代 CSS 原生 `conic-gradient` 矢量甜甜圈算法重构圆环图：
  1. 依据各分类支出金额占总金额比例，动态计算扇区角度（$0^\circ \sim 360^\circ$）。
  2. 运用多层色彩 stops 动态拼接 CSS 原生渐变，配合中央镂空与浮层展示当月收支总额与类型标签。
  3. 彻底摆脱庞大的 Canvas 脚本依赖，实现零卡顿、跨端 100% 渲染一致。
- **验证结果**：支出与收入图表完美呈现 Apple 级优雅圆环，分类色块过渡平滑，真机实测 60fps 流畅呈现。

## 5. 核心业务红线验证详情

### 5.1 金额存储（分/元）验证
通过在真机上录入 50.50 元餐饮支出，并触发离线同步，直接在 MySQL 容器中执行查询：
```sql
SELECT id, book_id, amount, remark, deleted FROM t_transaction ORDER BY create_time DESC LIMIT 1;
```
- **数据库落盘值**：`amount = 5050`
- **验证结论**：严格符合“前端展示元、传输存储分（$50.50 \times 100 = 5050$）”规范。

### 5.2 逻辑删除验证
在真机上删除上述记录，触发同步后再次查询数据库：
```sql
SELECT id, deleted FROM t_transaction WHERE id = '...';
```
- **数据库状态**：`deleted = 1`，数据行物理保留。
- **前端状态**：本地 SQLite/缓存与 UI 列表即时过滤，不再展示。
- **验证结论**：逻辑删除规则 100% 遵从，未发生物理硬删除。

### 5.3 多账本硬隔离验证
- **测试步骤**：日常账本拥有多笔历史消费记录，切换至旅游账本后，流水列表立即显示空状态。在旅游账本新增一笔交通消费后，切换回日常账本，该交通消费完全不出现在日常账本中。
- **验证结论**：`book_id` 硬隔离生效，数据完全独立。
